# 06 安全與權限

> 狀態：已實作。稽核紀錄存在閘道自己的 D1，保留 30 天，寫入時清除；服務拋錯與可預期的失敗（找不到、重複）都記 `error`。

## 閘道是單點

閘道持有所有服務的 binding 與金鑰，被攻破就等於所有服務都被打開。因此：

- 閘道只放 MCP、OAuth、登入，不放其他功能，減少可被攻擊的程式碼。
- 閘道的登入要用強密碼或 Passkey，密碼用 `wrangler secret` 保存。
- 每個服務**自己仍要守住範圍**：RPC 或內部路由只開放資料操作，不開放改設定、建帳密、管 Passkey、寄信設定。閘道被攻破時，損害也只到這些操作為止。

## 最小權限

- 授權範圍分讀、寫：`<服務>:read`、`<服務>:write`。同意頁預設只勾讀取。
- 閘道依 token 的範圍過濾 `tools/list`，看不到的 tool 也呼叫不到；`tools/call` 時再檢查一次範圍，不只依賴列表。
- 刪除類 tool 標上 MCP 的 `destructiveHint`，讀取類標上 `readOnlyHint`，讓 client 在執行前提示你確認。

### 有成本或對外動作的操作另開範圍

有些操作不改資料，但會花錢或碰外部世界，例如書籤的預覽會抓外部網頁、呼叫 Workers AI。這類操作不歸在 `:read`，也不併進 `:write`，而是另開一個**以動作命名**的範圍：

| 範圍 | 允許 | 書籤服務的 tool |
|---|---|---|
| `bookmarks:read` | 查詢既有資料，不花 AI 額度、不連外 | `bookmarks_search`、`bookmarks_get`、`bookmarks_overview` |
| `bookmarks:fetch` | 抓外部網頁、用 AI 整理 | `bookmarks_add` 的自動抓取 |
| `bookmarks:write` | 新增 | `bookmarks_add` |

- `bookmarks_add` 需要 `write`；只給網址、交給伺服器自動抓取與整理時，還要再有 `fetch`。沒有 `fetch` 的 token 只能自己帶標題新增。
- 會連外的 tool（`bookmarks_add`）標上 MCP 的 `openWorldHint`。
- 預覽、修改、刪除沒有對應的 tool，原因見〈提示注入〉。

**為什麼不叫「進階讀取」**：OAuth 的範圍名稱沒有統一標準，MCP 規範也只規定怎麼傳遞範圍，不規定怎麼命名。常見的大型 API（GitHub、Google、Slack）都是「資源 + 動作」的細粒度範圍，沒有「進階」這種分級。用動作命名，看名稱就知道授權了什麼，日後別的服務也能照同一規則另開自己的動作範圍（例如 `<服務>:send`）；分級式的名稱則說不清楚包含哪些操作，加新功能時也很難判斷該歸到哪一級。

## 提示注入（Prompt Injection）

書籤的標題與摘要來自外部網頁加上 AI 整理，原樣回傳給 AI client。惡意網頁可以在內容裡寫指令，誘導 agent 呼叫刪除或修改。

接上多個服務後風險更大：一個服務回傳的內容，可能誘導 agent 去操作另一個服務。

- 只需要查詢的 client，只授權 `:read`。
- 回傳內容時把外部來源的欄位與系統資訊分開，tool 說明裡註明這些欄位來自外部網頁。
- 跨服務的寫入，由 client 端逐次確認，不設成自動核准。

書籤服務因此只開放查詢與新增，三個 tool 不提供：

| 不提供的 tool | 被誘導時的後果 |
|---|---|
| 預覽網址 | agent 把讀到的書籤內容塞進網址參數，伺服器照著去抓，資料就送到對方主機 |
| 修改 | 書籤內容被改掉 |
| 刪除 | 書籤被刪掉，無法復原 |

新增還留著，被誘導時最多多出幾筆書籤，每筆都會寄通知信，看得到也刪得掉。只給網址的新增同樣會連外，所以 `bookmarks:fetch` 預設不勾。

## 頻率限制

兩層，各守各的：

- **閘道**：同一個 OAuth client 兩次新增之間至少隔 3 秒，查詢不限（依 tool 有沒有標 `readOnlyHint` 判斷）。還在間隔內的呼叫不執行，回 tool 錯誤結果請 client 排隊，稽核紀錄記 `throttled`。
- **書籤服務**：抓取與寫入各有一組全站共用的名額，不分來源；RPC 回 `rate_limited`，閘道轉成同樣的排隊提示。

兩層都把時間戳存 D1，用條件式寫入判斷，同時進來的呼叫只有一個放行。

## 同帳號的信任邊界

RPC 不驗呼叫者。具名 entrypoint 沒有公開網址，知道服務的網址也打不到；能呼叫的只有同一個 Cloudflare 帳號裡宣告了服務綁定的 Worker。所以：

- Cloudflare 帳號開兩步驟驗證，API token 只給用得到的權限並設期限。
- `caller` 是呼叫端自己填的，只當紀錄。
- RPC 只取契約內的欄位，多帶的不採用；參數型別與範圍在服務端自己驗。

## 回傳什麼

- 書籤的 `share_id` 拿到就能免登入瀏覽中轉頁，預設不回傳；需要分享網址的 tool 再明確提供。
- 錯誤訊息只回說明文字，不回堆疊與內部路徑。

## 稽核紀錄

| 記在哪 | 記什麼 |
|---|---|
| 閘道 | 時間、OAuth client、tool 名稱、結果狀態、處理時間 |
| 各服務 | 由閘道傳入的 client 識別、操作、影響到的資料 id |

兩邊都不記請求內容（備註、網頁內文），理由跟書籤服務現有的呼叫紀錄一樣：避免把個人資料複製進 log。

## 效期與撤銷

- access token 設短效期，靠 refresh token 延長；不用的 client 在閘道設定頁撤銷。
- 更換閘道密碼不會撤銷已發出的 token，懷疑外流時要一併撤銷所有授權。
- HMAC 金鑰外流時，只換那個服務的金鑰（見 [04](04-多服務串接與金鑰.md) 的輪替做法）。
