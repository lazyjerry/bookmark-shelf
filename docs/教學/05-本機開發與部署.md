# 05 本機開發與部署

> 狀態：本機開發已實作，部署尚未進行。與下面說明的差異：書籤服務的 `ai` binding 一律走遠端，帳號不只一個時在非互動環境會啟動失敗，`--local` 也關不掉；本機整合驗證改用拿掉 `ai` 的暫時設定檔，兩個 Worker 共用 `--persist-to .wrangler/state`，D1 migration 要對同一個 persist 目錄各套一次。「兩個終端機各跑一個」的方式還沒驗證。

## 專案放哪裡

閘道是串接多個服務的入口，不屬於書籤服務，建議放在**獨立的 repo**。書籤服務這邊只多一個 `BookmarkRpc` entrypoint。

```
<閘道 repo>/
├── wrangler.jsonc        services（各服務的 binding）、kv_namespaces（OAUTH_KV）
├── src/index.ts          OAuthProvider 的 default export
├── src/auth.ts           登入頁、同意頁（defaultHandler）
├── src/mcp.ts            MCP server 與 tools（apiHandler）
└── src/services/         每個服務一份：RPC 介面或 HMAC 呼叫、tools 定義
```

## 本機一起跑

本機的 `wrangler dev` 也支援服務綁定，有兩種方式：

- **兩個終端機各跑一個**：先在書籤服務目錄跑 `wrangler dev`，再到閘道目錄跑 `wrangler dev`。wrangler 會透過本機的 dev registry 把閘道的 binding 接到正在跑的書籤服務。
- **一個指令同時跑**：在閘道目錄執行 `wrangler dev -c wrangler.jsonc -c <書籤服務路徑>/wrangler.jsonc`，第一個 `-c` 是對外提供 HTTP 的主 Worker。

書籤服務本機測試的既有做法照舊：獨立的 D1（`--persist-to`）、測試用的 `AUTH_PASS`、`AI_ENABLED=false`。

驗證用 MCP Inspector 連 `http://localhost:<port>/mcp`，走一次授權流程，再逐一呼叫 tools。

## 部署順序

1. **先部署被呼叫的服務**：書籤服務帶著 `BookmarkRpc` 先上線（`npm run deploy`）。閘道的 binding 指向一個還不存在的 entrypoint，呼叫時會失敗。
2. **建立閘道的 KV 與密鑰**：

   ```bash
   wrangler kv namespace create OAUTH_KV     # 把回傳的 id 填進 wrangler.jsonc
   wrangler secret put GATEWAY_PASS
   wrangler secret put SVC_<服務>_KEY        # 只有走 HMAC 的服務需要
   ```

3. **部署閘道**，並在閘道網域上設定自訂網域（Passkey 的 `rpID` 綁這個 hostname，之後換網域就要重新註冊 Passkey）。
4. **接上 AI client**：
   - Claude Code：`claude mcp add --transport http <名稱> https://<閘道網域>/mcp`，第一次使用時會開瀏覽器走授權。
   - claude.ai、Claude Desktop、ChatGPT：在 connector 設定加入 `https://<閘道網域>/mcp`。

## 改 RPC 介面時

RPC 方法是兩個服務之間的契約，改簽名要照這個順序，避免中間有一段時間互相對不上：

1. 服務端**新增**新方法或可選參數，保留舊的，部署。
2. 閘道改用新方法，部署。
3. 確認沒有呼叫舊方法後，服務端再移除舊方法。
