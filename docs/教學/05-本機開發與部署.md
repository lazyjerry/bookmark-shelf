# 05 本機開發與部署

> 狀態：本機開發已實作，書籤服務已部署。與下面說明的差異：書籤服務的 `ai` binding 一律走遠端，帳號不只一個時在非互動環境會啟動失敗，`--local` 也關不掉；本機整合驗證改用拿掉 `ai` 的暫時設定檔，兩個 Worker 共用 `--persist-to .wrangler/state`，D1 migration 要對同一個 persist 目錄各套一次。暫時設定檔的路徑列在閘道的 `.dev.services`。「兩個終端機各跑一個」的方式還沒驗證。

## 專案放哪裡

閘道是串接多個服務的入口，不屬於書籤服務，建議放在**獨立的 repo**。書籤服務這邊只多一個 `BookmarkRpc` entrypoint，自己的 tool 定義也放在這邊（`src/tools.ts`）。

```
<閘道 repo>/
├── wrangler.example.jsonc 進版控的範例：kv_namespaces（OAUTH_KV）等，不含 services
├── wrangler.jsonc        不進版控：從範例複製，在 services 填各服務的 binding
├── .dev.vars             不進版控：本機的密鑰與 SERVICES
├── .dev.services         不進版控：本機要一起跑的服務設定檔路徑
├── scripts/dev.sh        npm run dev：依 .dev.services 組出 wrangler dev 的指令
├── src/index.ts          OAuthProvider 的 default export
├── src/auth.ts           登入頁、同意頁（defaultHandler）
└── src/mcp.ts            MCP server（apiHandler）：向各服務 describe() 要 tool 清單，執行時呼叫 call()
```

閘道 repo 不含任何服務專屬的程式，也不記接了哪些服務。tool 與授權範圍由各服務的 `describe()` 提供（見 [02](02-服務綁定與RPC.md)〈服務自述〉），接了哪些服務則分兩處，都在版控外：

- **服務綁定**：repo 只追蹤 `wrangler.example.jsonc`，裡面沒有 `services`；實際的 `wrangler.jsonc` 列入 `.gitignore`，從範例複製後在 `services` 填 binding 名稱、Worker 名稱與 entrypoint。閘道的 `npm test` 與 `npm run typecheck` 讀範例檔，不需要這份本機設定。
- **服務清單**：`SERVICES` 是逗號分隔的 binding 名稱，本機寫在 `.dev.vars`，線上用 `wrangler secret put SERVICES`。沒設定時閘道照常運作，只是沒有任何 tool 與範圍。

服務端要實作的契約與串接步驟，閘道那邊寫在它自己的 `README.dev.md`；閘道的文件不提書籤服務，也不連到這個資料夾。

## 本機一起跑

本機的 `wrangler dev` 也支援服務綁定，有兩種方式：

- **兩個終端機各跑一個**：先在書籤服務目錄跑 `wrangler dev`，再到閘道目錄跑 `wrangler dev`。wrangler 會透過本機的 dev registry 把閘道的 binding 接到正在跑的書籤服務。
- **一個指令同時跑**：在閘道目錄執行 `npm run dev`。它執行 `scripts/dev.sh`，讀 `.dev.services` 的每一行各加一組 `-c`，等同 `wrangler dev -c wrangler.jsonc -c <服務設定> ...`，第一個 `-c` 是對外提供 HTTP 的主 Worker。

`.dev.services` 一行一個服務的 wrangler 設定檔路徑，`#` 開頭是註解：

```
# 書籤服務（拿掉 ai binding 的暫時設定檔）
<書籤服務路徑>/<暫時設定檔>.jsonc
```

閘道的測試不靠這份設定：它接閘道 repo 內的範例服務 `test/fixtures/services.js`（auxiliary worker，經服務綁定走真的 RPC），不建置書籤服務。

書籤服務本機測試的既有做法照舊：獨立的 D1（`--persist-to`）、測試用的 `AUTH_PASS`、`AI_ENABLED=false`。

驗證用 MCP Inspector 連 `http://localhost:<port>/mcp`，走一次授權流程，再逐一呼叫 tools。

## 部署順序

1. **先部署被呼叫的服務**：書籤服務帶著 `BookmarkRpc` 先上線（`npm run deploy`）。閘道的 binding 指向一個還不存在的 entrypoint，呼叫時會失敗。
2. **建立閘道的 KV 與密鑰**：

   ```bash
   wrangler kv namespace create OAUTH_KV     # 把回傳的 id 填進本機的 wrangler.jsonc
   wrangler secret put GATEWAY_PASS
   wrangler secret put SERVICES              # 逗號分隔的 binding 名稱，例如 BOOKMARKS
   wrangler secret put SVC_<服務>_KEY        # 只有走 HMAC 的服務需要
   ```

3. **部署閘道**，並在閘道網域上設定自訂網域（Passkey 的 `rpID` 綁這個 hostname，之後換網域就要重新註冊 Passkey）。
4. **接上 AI client**：
   - Claude Code：`claude mcp add --transport http <名稱> https://<閘道網域>/mcp`，第一次使用時會開瀏覽器走授權。
   - claude.ai、Claude Desktop、ChatGPT：在 connector 設定加入 `https://<閘道網域>/mcp`。

## 改 RPC 介面時

閘道與服務之間的契約只有 `describe()`、`call()` 兩個方法的形狀。新增、調整、移除 tool 或授權範圍不算改契約：改服務的定義並部署，閘道不必重新部署。閘道把 `describe()` 的結果在同一個 isolate 留 60 秒，所以改動最多一分鐘後生效。

要改這兩個方法本身的簽名或回傳形狀時，照這個順序，避免中間有一段時間互相對不上：

1. 服務端**新增**新方法或可選參數，保留舊的，部署。
2. 閘道改用新方法，部署。
3. 確認沒有呼叫舊方法後，服務端再移除舊方法。
